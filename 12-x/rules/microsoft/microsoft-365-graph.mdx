## Rule Example

Below is an example of a rule definition for **Graph Admin Role Assignment Detected** ([view in repository](https://github.com/utmstack/UTMStack/blob/v12/definitions/rules/o365_graph/graph_admin_role_assignment.yaml)):

```yaml
# Rule version v1.1.0

dataTypes:
  - o365-graph
name: Graph Admin Role Assignment Detected
impact:
  confidentiality: 3
  integrity: 3
  availability: 1
category: Privilege Escalation
technique: "T1098.003 - Account Manipulation: Additional Cloud Roles"
adversary: origin
references:
  - https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-audit-activities
  - https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/permissions-reference
  - https://attack.mitre.org/techniques/T1098/003/
description: |
  An Entra ID administrator role, or eligibility for one, was granted to a user or a service principal. Attackers who gain an administrative session often give a second account or an application a privileged role so they keep control after the first account is cleaned up. Routine just-in-time activations of an existing eligibility are not reported.

  One alert is raised per account that receives a role; further roles for the same account within seven days are suppressed, because administrators often grant several roles at once.

  Next Steps:
  1. Confirm with the person who made the change (origin user) that the assignment was planned and approved.
  2. Check the account that received the role (target user, or log.targetDisplayName for an application) for recent sign-ins from unusual places.
  3. Remove the role if it is not justified, and review what the account did with it.
where: |
  equals("log.graphSource", "directory-audit") &&
  equals("actionResult", "success") &&
  oneOf("action", ["Add member to role", "Add eligible member to role", "Add member to role scoped over Restricted Management Administrative Unit", "Add member to role in PIM completed (permanent)", "Add member to role in PIM completed (timebound)", "Add eligible member to role in PIM completed (permanent)", "Add eligible member to role in PIM completed (timebound)"]) &&
  (regexMatch("log.roleName", "(?i)(administrator|partner tier[12] support|directory writers)") ||
   (equals("log.targetType", "Role") && regexMatch("log.targetDisplayName", "(?i)(administrator|partner tier[12] support|directory writers)")))
deduplicateBy:
  - lastEvent.log.targetId

```

### Graph Admin Role Assignment Detected

Attackers who gain an administrative session often give a second account or an application a privileged role so they keep control after the first account is cleaned up. ### Graph Application Consent Granted

A user or an administrator consented to an application in Entra ID, giving it access to company data. Illicit consent phishing tricks users into approving a malicious application that then reads mail and files through Microsoft Graph without needing the user's password. Admin consent is recorded in log.targetResources (ConsentContext.IsAdminConsent) and grants the access for every user.

One alert is raised per application; further consents to the same application within seven days are suppressed, because many users often consent to one new application in the same hour.

- **Category:** Initial Access
- **Technique:** T1528 - Steal Application Access Token
- **Impact:** C:3 / I:2 / A:1
- **Rule file:** [graph_app_consent_granted.yaml](https://github.com/utmstack/UTMStack/blob/v12/definitions/rules/o365_graph/graph_app_consent_granted.yaml)
- **Reference:** [https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-audit-activities](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-audit-activities)

### Graph Application Credential Added

A secret or certificate was added to an existing application registration or service principal in Entra ID. A new credential lets whoever holds it sign in as the application, with all its permissions, without any user password or multi-factor prompt. Attackers use this to keep access to mail and files after a compromise.

Entra ID writes the activity name with a long dash and a trailing space ("Update application – Certificates and secrets management "), so the rule matches the name by pattern. Creating a brand new application with a secret is not reported.

One alert is raised per person or application making the change; repeats within seven days are suppressed, because automated secret rotation updates many applications at once.

- **Category:** Persistence
- **Technique:** T1098.001 - Account Manipulation: Additional Cloud Credentials
- **Impact:** C:3 / I:3 / A:1
- **Rule file:** [graph_app_credential_added.yaml](https://github.com/utmstack/UTMStack/blob/v12/definitions/rules/o365_graph/graph_app_credential_added.yaml)
- **Reference:** [https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-audit-activities](https://learn.microsoft.com/en-us/entra/identity/monitoring-health/reference-audit-activities)

An Entra ID Conditional Access policy was created, changed or deleted. These policies decide who must use multi-factor sign-in and from where; an attacker with administrator access weakens or removes them, or adds an exclusion, so stolen credentials keep working.

One alert is raised per person and kind of change (create, update, delete); repeats within seven days are suppressed, because administrators often roll out several policies together.

The destination is in log.forwardingAddress and the rule in log.ObjectId.

### Graph Mailbox Full Access Granted

A person was given full access to another mailbox with Add-MailboxPermission. Full access lets them read every message in it; attackers grant it to an account they control to keep reading a target's mail. The mailbox is in log.ObjectId and the account that received access in log.permissionGrantee. Changes made by Exchange's own service accounts (NT SERVICE, NT AUTHORITY) while it provisions system mailboxes are not reported.

One alert is raised per person granting access; repeats within seven days are suppressed, because administrators often grant access to many mailboxes in one session.

- **Category:** Persistence

### Graph Password Spray from One Address

One address had at least 50 Entra ID sign-ins fail with a wrong user name or password (error 50126) within 30 minutes. Spraying tries a few common passwords against many accounts from the same address. The threshold sits above the busiest real day measured on customer Office 365 tenants, where a company gateway reached 20 such failures in half an hour.

Graph publishes sign-ins up to ten minutes late and in batches, so the count looks back 30 minutes. One alert is raised per address; repeats are suppressed for seven days.

- **Category:** Credential Access
- **Technique:** T1110.003 - Brute Force: Password Spraying
- **Impact:** C:3 / I:2 / A:2
- **Rule file:** [graph_signin_password_spray.yaml](https://github.com/utmstack/UTMStack/blob/v12/definitions/rules/o365_graph/graph_signin_password_spray.yaml)

### Graph Sensitive Application Permission Granted

An application was granted a Microsoft Graph or Exchange permission that reaches every mailbox, every file or the directory itself (for example Mail.Read, Files.ReadWrite.All, RoleManagement.ReadWrite.Directory or full_access_as_app). Application permissions work without a signed-in user, so an application holding one can read or change data across the whole company. Attackers grant these to an application they control to keep silent access.

The permission is in log.appRoleValue (application permission) or log.permissionScope (delegated permission granted for all users). One alert is raised per application and permission; repeats are suppressed for seven days.

- **Category:** Privilege Escalation
- **Technique:** T1098.003 - Account Manipulation: Additional Cloud Roles
- **Impact:** C:3 / I:3 / A:1

### Graph User Opened a Malicious Link

A user opened a link that Safe Links rated as phishing or malware (log.ThreatTypes), either because the click was allowed or because the user continued past the warning page. The user may have entered credentials or downloaded malware.

One alert is raised per user and link; repeats are suppressed for seven days.

- **Category:** Initial Access
- **Technique:** T1204.001 - User Execution: Malicious Link
- **Impact:** C:3 / I:2 / A:1
