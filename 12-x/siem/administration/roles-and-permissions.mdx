UTMStack v12 controls what each user can do with roles. A role is a named set of permissions, and a user can hold several roles. UTMStack ships three built-in roles, and you can create your own. This page lists every permission and what each built-in role includes.

## Where to manage roles

Go to **Configure > Team** and open the **Roles & permissions** tab. The tab lists every role with its number of permissions and modules, and a **Permission matrix** that shows what each role can do, module by module.

| Permission | Allows |
|---|---|
| `roles.read` | See roles and the list of permissions |
| `roles.write` | Create, edit and delete your own roles |

To give a role to a user, see **Users**.

## Built-in roles

The three built-in roles are the same in every tenant. They are marked **System** and cannot be edited or deleted.

| Role | Identifier | Purpose | Permissions |
|---|---|---|---|
| Administrator | `ROLE_ADMIN` | Full access, including users, roles and configuration | All 42 |
| Analyst | `ROLE_ANALYST` | Runs the security operations: triages alerts, works incidents and launches response actions | 27: every read permission, plus `alerts.write`, `incidents.write`, `soar.write`, `loganalyzer.write`, `dashboards.write` and `notifications.write` |
| Viewer | `ROLE_VIEWER` | Reads everything and changes nothing | 21: every read permission |

What this means in practice:

- **Analysts** cannot change users, roles, settings, identity providers, correlation rules, pipelines, integrations, data sources, compliance or retention.
- **Analysts** can run commands on agent hosts through the **Interactive Console**, because it uses `soar.write`. They cannot start a response flow by hand: that needs `soar.execute`, which only the Administrator role has.
- The SOC-AI assistant and its **Ask** buttons appear in the interface only for users who hold `socai.write`, which among the built-in roles only **Administrator** has. See **AI Providers**.

## Things that need the Administrator role itself

A few things are tied to the **Administrator** role, not to a permission. A custom role with the same permissions does not give them.

- The **Configure** menu (Data Sources, Integrations, Alerting Rules, Pipelines, Data Processing, Team and Settings) is shown only to users with the Administrator role.
- Viewing and regenerating the **Connection Key**.
- Setting **Support access** for a customer tenant (see **Support Access**).
- Operator-only pages and actions (the licence, data retention, the ThreatWinds switches, tenants) need the Administrator role in the default tenant. See **Settings Overview**.

## Create a custom role

<Steps>

<Step title="Start a new role">

Go to **Configure > Team**, open **Roles & permissions** and click **New role**.

</Step>

<Step title="Name the role">

| Field | What to enter |
|---|---|
| Identifier | A unique name used in the API, 2 to 50 characters. It starts as `ROLE_`; complete it, for example `ROLE_AUDITOR`. |
| Display name | The name people see, for example `Auditor` |
| Description | What the role is for |

</Step>

<Step title="Choose the permissions">

Under **Permissions**, tick the permissions the role needs. Use **all** to select every permission of a module.

</Step>

<Step title="Save">

Click **Save role**, then give the role to users on the **Members** tab.

</Step>

</Steps>

To change a custom role, click **Edit** on it. To remove it, click **Delete**. Users who hold only that role are left without access to any module.

Custom roles belong to the tenant they were created in. You see "Role created", "Role updated" or "Role deleted"; "role name is already in use" means the identifier is taken, and "System roles cannot be modified" appears if you try to change a built-in role, and also when your own roles lack `roles.write`.

## Which permissions each screen needs

Apart from a few places (the SOC-AI assistant, identity alias actions in the User Auditor and some integration controls), the interface does not hide buttons by permission. A user who lacks a write permission usually still sees the button, and gets "You do not have permission to do that" or a similar error when using it. Use this table to give each role what its screens need.

| Screen | To view | To change |
|---|---|---|
| Overview (home page) | `alerts.read` and `loganalyzer.read` for the alert cards; the other cards need `datasources.read`, `eventprocessing.read`, `incidents.read`, `soar.read` and `compliance.read` | |
| Alerts, tags and tagging rules | `alerts.read` and `loganalyzer.read` | `alerts.write` |
| Incidents | `incidents.read` | `incidents.write` |
| Log Explorer | `loganalyzer.read` | `loganalyzer.write` for saved searches |
| Dashboards | `dashboards.read` | `dashboards.write`; the widget editor also needs `loganalyzer.read` |
| Automated response flows and execution history | `soar.read` | `soar.write`; `soar.execute` to run a flow by hand |
| Interactive Console | `soar.write` | `soar.write` to run commands on agents |
| Compliance | `compliance.read` | `compliance.write` |
| Threat intelligence | `threatintel.read` | |
| User Auditor | `adaudit.read` | `adaudit.write` |
| Data Sources | `datasources.read` | `datasources.write` |
| Integrations | `integrations.read` | `integrations.write` |
| Alerting Rules, Pipelines, Data Processing | `eventprocessing.read` | `eventprocessing.write` |
| Team | `users.read`, `roles.read` | `users.write`, `users.delete`, `roles.write` |
| Notifications | `notifications.read` | `notifications.write` |

## Example custom roles

These examples show how to combine permissions for common jobs. Adjust them to your organization.

### SOC tier 1 analyst

Triages alerts and works incidents, but cannot run commands on endpoints or change flows.

`alerts.read`, `alerts.write`, `incidents.read`, `incidents.write`, `loganalyzer.read`, `loganalyzer.write`, `dashboards.read`, `notifications.read`, `notifications.write`, `soar.read`, `threatintel.read`, `adaudit.read`, `datasources.read`

Compared with the built-in **Analyst**, this role cannot use the Interactive Console or edit dashboards.

### Incident responder

Everything a tier 1 analyst can do, plus containment.

The tier 1 permissions, plus `soar.write` (create and change flows, run commands on agents through the Interactive Console) and `soar.execute` (run flows by hand).

The Interactive Console asks for the user's own UTMStack password before it runs commands. Users whose accounts were created by single sign-on have no UTMStack password, so give responders accounts with a local password if they need the console.

### Detection engineer

Writes and tests correlation rules and parsing pipelines.

`eventprocessing.read`, `eventprocessing.write`, `loganalyzer.read`, `loganalyzer.write`, `alerts.read`, `datasources.read`, `integrations.read`, `dashboards.read`, `dashboards.write`

Users with this role open **Alerting Rules** and **Pipelines** by address (see above).

### Compliance auditor

Reads compliance results and the audit trail, changes nothing.

`compliance.read`, `audit.read`, `dashboards.read`, `loganalyzer.read`, `alerts.read`, `incidents.read`

Users with this role open **App Audit Logs** by address.

## Tips for designing roles

- Give people the smallest role that lets them do their work. Start from **Viewer** and add permissions as needed.
- Treat `users.write` and `roles.write` as administrator rights: anyone who can create roles and assign them can give themselves any permission.
- `soar.write` lets the holder run commands on agent hosts through the Interactive Console. Give it only to people you trust with that access.
- Changes to a user's roles reach their open sessions within one hour, when their sign-in renews.
