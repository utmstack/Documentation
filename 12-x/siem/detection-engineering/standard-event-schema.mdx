Every log that UTMStack processes ends up as an event with the same set of field names, whatever product sent it. This shared layout is the standard event schema. Pipelines map vendor fields into it, and rules, dashboards, Log Explorer and compliance checks read from it, so a rule written for `origin.ip` works for every source that fills `origin.ip`.

## Event structure

An event has a set of top-level fields and three areas:

- `log`: vendor fields that have no standard place.
- `origin`: the side that started the activity (who or what acted).
- `target`: the side the activity was aimed at.

`origin` and `target` share the same list of fields.

## Top-level fields

| Field | Type | Description |
|---|---|---|
| `id` | Text | Unique identifier of the event (a UUID). |
| `@timestamp` | Date and time | The time carried by the incoming log, in RFC 3339 format (for example `2026-11-11T09:30:00Z`), in UTC. No pipeline step can change it. |
| `deviceTime` | Date and time | The time recorded by the source device. If no pipeline sets it, the engine copies `@timestamp` into it. |
| `dataType` | Text | The kind of log, for example `linux`, `wineventlog` or `firewall-fortigate-traffic`. It decides which pipelines and rules run. |
| `dataSource` | Text | The device or integration that sent the log, for example the host name of a machine with an agent. |
| `tenantId` | Text | The tenant the event belongs to. |
| `tenantName` | Text | The tenant's name. The engine fills it in. |
| `action` | Text | The activity, for example a login, a file change or a connection. |
| `actionResult` | Text | The outcome: `success`, `failed` or `denied`. See below. |
| `protocol` | Text | Network protocol, for example `tcp`, `udp` or `http`. |
| `connectionStatus` | Text | State of the connection, for example established or closed. |
| `statusCode` | Whole number | A numeric status, for example HTTP `404`. |
| `severity` | Text | The importance the source gave the event. UTMStack does not enforce a list of values. |
| `raw` | Text | The original log text. Read-only: no step can change or delete it. |
| `log` | Object | Vendor fields with no standard place. |
| `origin`, `target` | Object | The two sides of the activity. See below. |
| `errors` | List of text | Messages from pipeline steps that failed on this event. |
| `compliance` | Map | Regulation names, each with a list of values. |

### Time fields

- `@timestamp` comes from the sender. The engine refuses a log whose time is missing or not in RFC 3339 format.
- `deviceTime` is stored as a date and time with millisecond precision. If a pipeline writes a value the database cannot read as a date, the database refuses the event. Always convert a vendor time with the `reformat` step before you write it to `deviceTime`. See **Pipeline File Format and Step Reference**.

### `actionResult` values

Write `actionResult` as exactly one of these values, or leave it empty:

| Value | Use it when |
|---|---|
| `success` | The action was completed. |
| `failed` | The action was attempted and did not work, for example a wrong password. |
| `denied` | The action was refused by a policy, a firewall or a permission check. |

Do not use other spellings such as `failure`, `fail` or `blocked`: rules compare these values as text. The threat intelligence check also reads this field: it skips events whose `actionResult` is `failed`, `denied` or `blocked`, and checks every other event, including events with no value. See **Threat Intelligence: How Indicator Alerts Work**.

### `dataSource` and assets

If `dataSource` equals the host name or IP address of one of your tenant's assets, the engine replaces it with the asset's name.

## The `log` area

`log` holds every vendor field that has no standard place, for example `log.eventCode` for a Windows event id or `log.message` for a syslog message. The `json`, `kv` and `xml` parsing steps write everything they extract under `log.`.

<Note>

UTMStack v12 uses `log.*` for these fields. Some UTMStack v11.3 filters used `event.*` instead; v12 does not.

</Note>

The type of a `log` field can differ from one event to the next: a value can be a number in one event and text in another.

## What is kept and what is dropped

When the last pipeline step has run, the engine turns the result into an event. Four rules decide what survives. They apply silently, so check your field names carefully.

| Rule | What happens | Example |
|---|---|---|
| Field names are cleaned | Every character other than letters, digits, dots and underscores is removed from a field name. | `log.event-type` becomes `log.eventtype`. `log.event_type` is kept as it is. |
| Unknown names are dropped | A field outside `log` whose name is not in the schema is removed, with no error. | `origin.hostname` is dropped; the schema field is `origin.host`. |
| A wrong type drops the event | If a schema field holds a value of the wrong type, the whole event is discarded and the engine logs "failed to convert log to event". | A word in `origin.port`. Use the `cast` step to convert ports to `int`. |
| `raw` and `@timestamp` are protected | No step can change or delete them. | A `delete` step on `raw` does nothing. |

An unreadable `deviceTime` also loses the event: the database refuses it (see **Time fields**).

## How events are stored

Events are stored in the ClickHouse table `logs`. Knowing the columns helps when you write SQL in Log Explorer or compliance checks:

| Column | Notes |
|---|---|
| `tenantId`, `@timestamp`, `dataType`, `dataSource`, `id`, `deviceTime`, `tenantName` | One column each. |
| `protocol`, `connectionStatus`, `action`, `actionResult`, `severity` | One column each. |
| `statusCode` | Stored as text. |
| `errors` | List of text. |
| `origin`, `target`, `compliance`, `log` | JSON columns. `log` keeps up to 512 typed paths. |
| `raw` | The original text. |

See **Log Explorer SQL Mode**.

## Good practice for mapping

1. **Map every address.** Put IP addresses in `origin.ip` and `target.ip`, host names in `origin.host` and `target.host`, and user names in `origin.user` and `target.user`. Rules, threat intelligence and dashboards read these fields.
2. **Use the exact `actionResult` values.** Write `success`, `failed` or `denied`, nothing else.
3. **Convert times and numbers.** Use `reformat` before writing `deviceTime`, and `cast` to `int` before writing ports or counters.
4. **Keep vendor detail under `log`.** Only move a value out of `log` when a standard field fits it.
5. **Use `compliance`** to tag events with regulation names and values.
6. **Rely on `raw`.** The original text is always kept, so you can check your parsing against it.
