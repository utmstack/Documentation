UTMStack v12.0.2 ships 94 ready-made response flows. They all arrive switched off. 13 of them have a trigger and can run on their own once you switch them on; the other 81 have a placeholder trigger on purpose and run only when you start them by hand or after you copy them and give the copy a trigger.

## What you need to know first

- Shipped flows (shown with a lock icon on the **Flows** page and listed on its **System** tab) cannot be edited or deleted. To change one, copy it with **New flow > From an existing one**. The copy is saved switched off and is yours to edit.
- Each tenant switches shipped flows on separately.
- Shipped flows act for real: they block addresses, disable or expire accounts, stop processes, isolate machines and shut them down. Read every command in the **Code** tab before you use a flow.
- Many shipped commands put quotes around a placeholder, for example `remoteip="$(alert.adversary.ip)"`. With the automatic quoting of UTMStack v12.0.2 those values arrive with extra quote characters. Remove the quotes around placeholders in your copy. See **Placeholders**.
- Several commands were converted from UTMStack v11 and read fields that an alert may not carry (for example process names from the event). A placeholder that cannot be filled in is sent as written. Test a copy with **Trigger flow** against a real alert before you switch it on.

> [!DANGER]
> Do not switch on a shipped flow to try it out. Use **Trigger flow** on a test machine instead (see **Flows Page**). A switched-on flow runs on every matching alert, on the machine that raised it.

## Flows without a trigger

The other 81 flows have the trigger `name IS TODO-set-the-correlation-rule-that-triggers-this`. No alert has that name, so they never start on their own. The file header explains why: a broad condition would run these destructive actions on every alert, and choosing which detection should run them is your decision.

You can use them in two ways:

1. **Copy and complete.** Copy the flow, set a real trigger (usually the alert name of one correlation rule), remove quotes around placeholders, check the platform and shell, test with **Trigger flow**, then switch the copy on.
2. **Run by hand from an alert.** The lightning button in an alert's row in **Threat Management > Alerts**, and the lightning button in the side panel of **Live Operations**, look for the shipped flow made for that kind of alert and the host's platform. The button shows the flow's name ("Finding a response…" while it looks, "No system flow covers this alert" when there is none). Click it to start that flow once on the alert's host. You see "Response triggered" or "Could not trigger the response". This is a manual start, so it needs the `soar.execute` permission (Administrator role), and it works even though the flow is switched off.

## Ready-made commands in the editor

Besides the shipped flows, the editor palette has nine ready-made shell steps for each platform (isolate, shut down, kill a process, log a user out, disable a user, block an address, restart, uninstall a package, remove a file). See **Building a Flow**.

## Changed from UTMStack v11

- The 23 playbooks and 73 action templates are replaced by these 94 flows.
- Placeholders were rewritten to start with `alert.`, for example `$(alert.adversary.ip)`.
- Several former playbooks no longer have a trigger: Windows Defender Exclusions Added via PowerShell, Windows Defender: Protection Disabled, Windows: Disabling Windows Defender Security Settings via PowerShell, Windows: Disable Windows Firewall Rules via Netsh, Windows: Remote Desktop Enabled in Windows Firewall by Netsh, Windows: A user account was added to administration groups, Linux - Process Injection Techniques Detection, and Linux - CentOS/RHEL - CVE Vulnerability Detection in RHEL System.
